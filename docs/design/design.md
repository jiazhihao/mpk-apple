# Monolith — a megakernel inference engine for Apple silicon

*Design: MPK Runtime V2, re-derived for Apple GPUs from measurements.*

Status: draft 2026-09-19. "Monolith" is a working codename (one stone = one GPU-resident program); nothing depends
on it. Companion documents: [implementation plan](../../plans/implementation-plan.md) ·
[measured hardware facts](../research/apple-gpu-probes.md) · [survey of Apple inference systems](../research/apple-inference-systems.md).

First target: [`nvidia/Qwen3.8-27B-NVFP4`](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4), batch-1 decode latency,
M3/M4/M5 families, macOS 26+ (Metal 4). The engine is model-agnostic; Qwen3.8 is its first client.

Evidence tags: **[M]** measured by us on an M3 Pro ([probes](../research/apple-gpu-probes.md)); **[S]** Apple
spec/documentation; **[R]** third-party report; **[H]** hypothesis the plan must test.

## 0. Decisions at a glance

| # | Decision | Why (one line) |
|---|---|---|
| D1 | **Keep MPK's thesis, change its mechanism.** The whole generation loop — all layers, sampling, speculative accept/rollback, stop detection — is one *GPU-resident static program* with no CPU work and no CPU↔GPU synchronization on the critical path. It is **not** one never-returning kernel. | A running dispatch is never preempted or shared **[M]**; macOS kills compute that starves the display after ~0.5–1.2 s and any command buffer at ~5 s **[R]**; and no in-kernel barrier we could build is meaningfully cheaper than a dispatch boundary **[M]** |
| D2 | **Static schedule, generated by a compiler** from a model graph; never hand-written per model (PR #278's kernel is 22 k hand-written lines for one model). | Generality is a requirement. The dynamic dispatcher's benefit — absorbing skew across 148 SMs × 8 ranks — has no counterpart on one symmetric GPU running a dependency chain |
| D3 | **No role specialization of SIMD-groups ("warps").** One homogeneous compute crew; no loader, mma, storer or dispatcher roles. | Roles exist on NVIDIA to drive asynchronous engines and a software-managed scratchpad. Apple has neither: threadgroup memory is no faster than device memory **[M]**, there is no copy engine, and M5's neural accelerators are invoked *cooperatively by the calling threads* **[S]** — the conclusion the Hopper port already reached for `wgmma` |
| D4 | **Crew geometry = `num_gpu_cores` threadgroups × 384 threads** (12 SIMD-groups × 32 lanes) for every kernel. | One threadgroup runs per core and 12 SIMD-groups run at full speed per core **[M]** — the Apple analogue of "one 384-thread CTA per SM" |
| D5 | **One dispatch per fused op, encoded once into an indirect command buffer (ICB) and replayed.** The dispatch boundary is the barrier. Multi-op kernels with in-kernel barriers were built and measured; they are correct but never faster, so they are not used. | Dispatch boundary, including the launch of 6,912 threads: **1.6–2.7 µs**. In-kernel barrier: 2.1–2.6 µs with static slices (**3.1–3.9 µs** in the spec-compliant fenced form), 4.7–6.1 µs with stealing. With real block work every variant lands at 92–96.5 µs/op **[M]** — nothing to win, and a multi-op kernel is a long non-preemptible dispatch |
| D6 | **Short dispatches *and* short command buffers.** Other GPU clients never get in during a dispatch; they usually get in between dispatches, but in the worst case they wait for our whole in-flight command buffer. Command buffers carry ≤ ~16–33 ms of work while a display is attached (a tunable; more when headless). | A small dispatch on a second queue waited 1.2–1.4 s behind one long dispatch; behind 800 short dispatches in one command buffer it waited 0.3–0.5 ms in 5 of 6 trials and the full 1.13 s in the other; 130–140 ms outliers behind ~155 ms buffers **[M]** |
| D7 | **Self-advancing steps.** Everything that varies per step (positions, KV length, T, RNG counter, accept counts, done flag) lives in a GPU `StepState` updated by a serial op at the end of each step. The same ICB is replayed unchanged; the host only keeps the queue non-empty and drains a token ring. | Removes the CPU↔GPU sync (0.13 ms each **[M]**, plus the pipeline bubble) from sampling and from every speculative-decoding round |
| D8 | **Weights are re-laid-out at load time into a block-lane-major (BLM) pack** — the role MPK's TMA "swizzle" layouts play. A SIMD-group sweeps ~32–64 KB blocks; each lane reads one contiguous sub-range. | 124–134 GB/s (81–87 % of nominal), vs 59–60 GB/s for far-apart lane stripes and 106–126 GB/s for the best conventional geometry **[M]** |
| D9 | **Inside an op, SIMD-groups take static slices.** *Own-slice + steal* is available per op for uneven blocks or perturbed cores. | Stealing is exactly-once and as fast as static slicing even with half the crew missing **[M]**; static slices need no atomics and rely only on Metal's dispatch semantics |
| D10 | **Speculative decoding with the checkpoint's MTP head is a first-class milestone**, fully on the GPU. | Decode reads 17.6 GB/token; the bandwidth bound is ~7–9 tok/s on an M3 Pro. Verifying T = 2–4 tokens per weight pass is the only lever past it |
| D11 | **Numerics contract = weight-only dequantization (W4A16 / W8A16)**, BF16 residual stream, FP32 accumulators and recurrent state, one rounding per op output. Reference = HF model on the *dequantized* weights. | Apple GPUs have no FP4/FP8 arithmetic; the checkpoint's `input_scale`s are a Blackwell throughput feature, not a semantic requirement |
| D12 | **Profiling = per-op GPU timestamps** (every op is already its own dispatch) into MPK's `.mpktrace` format and viewer; a *clock SIMD-group* is available for intra-op traces. | MSL has no in-kernel clock; a free-running atomic tick counter gives ~48 ns ticks ±1 % **[M]** |
| D13 | **Stack:** C++/Objective-C++ runtime, Python front-end and compiler, MSL kernels specialized with function constants and cached in binary archives. Standalone repo; MPK code reused under Apache-2.0 where it fits; no MPK/Mirage naming. | Decided 2026-09-19 |
| D14 | **Inter-op overlap only where it is free:** an ALU-bound op and a bus-bound op that do not depend on each other are encoded as un-barriered sibling dispatches, both at full crew geometry. No weight pre-staging across dependencies (MPK V2's form of pipelining), and no hand-partitioning of cores. | The memory bus saturates with ~half of the M3 Pro's cores, so an ALU-bound op hides completely (86–114 %, within noise) inside a bus-bound one; two bus-bound ops overlapped gain 0 %; manual core splits were sometimes *slower* than serial **[M]** (§5.12) |

The two questions put to this design, answered in §7: **warp specialization — no**; **static megakernel — yes to
"static", no to "one kernel"**. On Apple silicon the megakernel is a pre-encoded, self-advancing GPU program of
fused whole-GPU dispatches.

## 2. What transfers from MPK, and what does not

MPK wins on NVIDIA by (i) removing kernel-launch cost and CPU↔GPU synchronization, (ii) scheduling hundreds of tasks
per op across 130–150 SMs while loader warps stream weights into a software-managed SMEM asynchronously, and
(iii) doing collectives in-kernel. We measured what each is worth on Apple silicon instead of assuming it.

| MPK benefit | On Apple silicon | Evidence |
|---|---|---|
| Launch overhead eliminated | **Already small for a large model.** Metal encodes a dispatch in 0.13 µs of CPU and executes its boundary in ~1.3–2.7 µs of GPU time (others report 2.6–5 µs on other chips **[R]**). A 1,240-dispatch token costs ~2 ms: 1–2 % of a 27B token on an M3 Pro, ~7 % at 30 ms/token — but 40–70 % of the token for 0.6–3 B models and 3B-active MoE, where today's engines sit at 22–57 % of the bandwidth bound **[R]**. What *is* expensive in existing engines is framework structure: MLX splits a decode step into 45–90 command buffers at ~20 µs each **[R]**. | P7, P10 **[M]**; [survey](../research/apple-inference-systems.md) §1, §5 |
| CPU↔GPU sync eliminated | **Real.** 0.13 ms per sync plus the bubble; decisive where an engine must sync every step: CPU-side sampling and, above all, every speculative-decoding round. | P7 **[M]** |
| Async data movement overlapped with compute | **Does not exist.** No copy engine, no fast scratchpad; the memory hierarchy is hardware-managed. | P8 **[M]**; Apple9+ "dynamic caching" **[S]** |
| Fine-grained dynamic task scheduling | **Moot.** Decode is a chain of ops that each want the whole memory bus; one device, no network skew. Intra-op balance is handled by stealing where needed. | §5.3 |
| One long-lived kernel | **Counter-productive.** Not preemptible, watchdog-limited, and its in-kernel barriers cost more than dispatch boundaries. | P6, P6b, P10 **[M]** |
| In-kernel collectives | Out of scope (single device). Thunderbolt-5 RDMA is CPU-driven send/recv **[S]**. | — |

Where the wins actually are on Apple — the ledger this design is built on:

1. **Streaming efficiency.** On dense 7B 4-bit decode llama.cpp reaches 57–80 % of nominal bandwidth depending on the
   chip (62 % M3 Max, 70 % M4 Pro, 80 % M5 Pro), and MLX's 4-bit GEMV kernel alone streams at 87 % on an M5 Pro; the
   practical ceiling is ~85–90 % **[R]**. The crew geometry sweeping block-lane-major packs reached 81–87 % on the M3 Pro
   in a raw-read microbenchmark, +5 % to +17 % over the best conventional geometry depending on the run **[M]**. To be confirmed
   with real kernels (**[H]**, plan M1). Honest sizing: for a dense-ish 27B model this lever is worth a few percent to
   ~15 %, and it is a *kernel-geometry and data-layout* property, not a megakernel property.
2. **Tokens per weight pass.** MTP speculative decoding with on-GPU accept/rollback: no sync per round, no host
   re-encode, recurrent-state rollback handled on the GPU. Expected 1.5–2.2× **[H]**.
3. **Whole-step static fusion.** ~1,240 framework-level ops → ~330 fused whole-GPU dispatches (norm folded into the
   GEMV input, gate+up+SiLU in one pass, the whole GDN mixer per head, residual adds as epilogues): fewer
   materializations, fewer barriers, fewer loads per weight.
4. **Zero CPU in the loop.** ICB replay costs 0.01 ms of host time per token **[M]**; sampling, acceptance and stop
   detection run on the GPU; the host never decides what runs next.

> A candid summary: what carries over from MPK is the *thesis* (compile the whole generation loop into a GPU-resident
> static program) and much of the *discipline* (layout for the streamer, fused task bodies, monotone state, staged
> numerical gates). What does not carry over is the *mechanism* — one persistent kernel with specialized roles —
> because every hardware reason for it is absent here, and the one thing it would save (launch overhead) is already
> ~1 % and is removed more cheaply by replaying a pre-encoded command stream.

### 5.1 The step program

A **step** is one forward pass over `T` tokens (T = 1 plain decode; T = k+1 when verifying k drafts; T ≤ T_max when
chunking a prompt) plus sampling and state advance. The compiler emits a **step program**: an ordered list of fused
ops, each one Metal dispatch with the crew geometry; ~330 for Qwen3.8 (5 per layer).

**Why ~330, and not 1 or 1,240.** A dispatch boundary is needed exactly where a consumer block reads data produced by
*other* blocks of the previous op — an all-to-all dependency — because every SIMD-group must finish the producer
before any may start the consumer. A GEMV is all-to-all on its input (each output row reads the whole input vector);
the token mixer is all-to-all on the projection feeding it (one head's q/k/v/z rows were computed by different row
blocks). Everything else is block-aligned and is fused into a neighbour. That leaves five stages per layer, for both
layer types:

| # | Dispatch | All-to-all on | Fused into it (block-aligned, no barrier) |
|---|---|---|---|
| 1 | stacked input projection (`in_proj_qkv|z|a|b`, or `q|k|v` + gate) | residual stream `h` | input RMSNorm scaling (its statistic comes from the previous op's epilogue) |
| 2 | token mixer (`gdn_mixer` per v-head, or `gqa_decode` per (q-head, KV-chunk)) | the projection outputs | conv + SiLU, L2-norm, gates, recurrence, gated norm — or q/k norm, RoPE, KV append, output gate |
| 3 | output projection | the mixer output | residual add; per-block partial Σh² for the next norm |
| 4 | `gate|up` projection | `h` | post-attention RMSNorm scaling; SiLU·mul |
| 5 | `down` projection | the MLP activation | residual add; per-block partial Σh² for the next layer |

64 × 5 = 320, plus embed, `lm_head`, the sampling combine and the per-step advance ≈ 325–330; each MTP draft token adds
~8. This is the **dependency depth of the model** in all-to-all stages, not an engine choice: it cannot go lower
without changing the math (RMSNorm between stages 3 and 4 is nonlinear, so they do not fold), and a barrier has to
exist at each of these points in *any* implementation — the only question is what implements it, and the dispatch
boundary is the cheapest we measured (§5.3). The count goes *up* if a fusion is not done: separate norm-statistic
reductions +128, a separate q/k-norm + RoPE + KV-append +16, unstacked mixed-format projections (FP8 `qkv|z` vs BF16
`a|b`) +48 — ≈ 520 worst case. One split is deliberate: §5.12 emits each mixer's gate projection as an un-barriered
sibling of the mixer core (+64 dispatches, no extra barrier) because that pair can overlap. At ~1.8 µs each, 330 vs 520 is ~0.3 ms per token, so those fusions are justified by
memory traffic and materializations, not by dispatch count. *The count is derived by hand from the graph; no compiler
exists yet to confirm it.*

* The program is encoded **once** into a compute ICB: pipeline, buffer bindings with offsets, threadgroup sizes, and
  a barrier wherever the compiler found a dependency (ICB dispatches are concurrent unless barriered **[S]**). A step
  is then one `executeCommandsInBuffer` — 0.01 ms of host time **[M]**. Metal 4 command buffers are re-encodable but
  not replayable **[S]**, so the ICB is the replay mechanism under both Metal 3 and Metal 4 encoders. ICBs have no
  `setBytes`, and their buffer-bind offsets are 32-bit **[R]**: every op reads a small parameter record from a buffer,
  and large weight buffers are addressed through 64-bit GPU addresses stored in that record (tier-2 argument buffers +
  one residency set) rather than through bind offsets.
* Prior art: tinygrad replays a per-step ICB; OpenAI's gpt-oss Metal reference encodes N decode iterations with GPU
  sampling and on-GPU token feedback into one command buffer; uzu and Apple's Core AI sample engine keep 1–3 steps in
  flight **[R]**. None compiles a general model into a replayed, self-advancing program; that is the gap this engine
  fills. If a driver bug makes ICB replay unusable, the same program is re-encoded per step (0.16 ms/token **[M]**,
  still no synchronization).
* Nothing in the encoded program changes between steps. Whatever varies is read from `StepState` (§5.4). Ops whose
  work grows (attention over a longer KV) keep the fixed crew geometry and loop over a dynamic number of blocks
  in-kernel, so no indirect dispatch or re-encode is needed.
* Each dispatch is short (≈ 0.4 ms on an M3 Pro for this model) and each command buffer replays a *range* of the ICB
  worth ≤ ~16–33 ms of work while a display is attached (`executeCommandsInBuffer:withRange:`; a profile tunable,
  larger when headless). Other GPU clients are normally served between our dispatches, but the measured worst case is
  a wait for one whole command buffer **[M]** — so its length, not the step's, bounds the stall we can cause. On the
  M3 Pro that is ~5–9 command buffers per step at a few tens of µs each; on fast chips or small models several steps
  fit in one.

### 5.2 Crew kernels

Every op is a **block body**: a pure function of `(block_id, lane, op_args, step_state)` that reads its inputs and
writes a disjoint part of its outputs. All kernels are dispatched as `num_cores × 384`, and each SIMD-group executes
its blocks.

* *Lockstep rule.* The 32 lanes of a SIMD-group share control flow, so a block is always executed by a whole
  SIMD-group and its trip counts are lane-uniform.
* *Block shape* is chosen per op by the compiler from the chip profile: GEMV/GEMM — R rows of the weight matrix
  (R = 8–32, ~32–64 KB of packed weights); attention — one (q-head, KV-chunk); GDN mixer — one v-head;
  elementwise — a fixed span; vocab argmax — a row range.
* *Op classes.* `MAP` (disjoint outputs per block); `REDUCE` (per-block partials, combined in block order by a small
  follow-up dispatch — deterministic); `SERIAL` (a one-SIMD-group dispatch: sampling finalize, accept/reject, state
  advance).
* *Slices.* SIMD-group `s` owns blocks `s, s+S, s+2S, …` (or a contiguous range when locality matters). No atomics;
  correctness rests only on Metal's guarantee that a dispatch completes before a barriered successor starts.

### 5.3 In-kernel synchronization: what we built, measured, and do not put on the hot path

The NVIDIA design lives on in-kernel synchronization, so we implemented it faithfully and measured it
(`probes/p10_claim_protocol`): 320 ops × 544 blocks in **one** dispatch, a barrier after every op.

* **It works.** *Own slice + steal*: each nominal SIMD-group owns a contiguous slice behind its own cursor, drains
  it by bounded `compare_exchange`, then steals from other slices in a per-SIMD-group permuted order; lane 0
  broadcasts each claim with `simd_broadcast_first`; a monotone `done` counter is the barrier. Exactly-once execution
  and zero timeouts in every configuration — including half the crew missing and 2×/4× surplus threadgroups — so
  co-residency of all threadgroups, a hard correctness requirement in NVIDIA MPK, is only a performance property
  here. A spec-compliant build (`coherent(device)` buffers, `atomic_thread_fence(mem_device, seq_cst,
  thread_scope_device)` at every publish and barrier exit, MSL 3.2) costs +0.6 to +1.7 µs per op. A single global claim
  cursor is *not* viable (CAS contention: +27 %).
* **It does not pay.** Per barrier: 2.1–2.6 µs with static slices (3.1–3.9 µs fenced, which is what the spec
  requires), 4.7–6.1 µs with stealing — against **1.6–2.7 µs for a dispatch boundary**, which also launches the 6,912
  threads. With 30 µs blocks every variant lands at 92–96.5 µs/op. A multi-op kernel is also one long non-preemptible
  dispatch (§0 D6) and is opaque to Apple's tools.

So the hot path uses dispatch boundaries. The protocol stays in the toolbox for two uses: **intra-op stealing** in
ops whose blocks are uneven (long-context attention, MoE experts) or when cores are perturbed, and re-evaluation on
chips where the trade-off might differ (plan M7, time-boxed).

### 5.4 GPU-autonomous control

`StepState` (one small buffer): `step`, per-sequence `position`, `kv_len`, `T_this_step`, `pending_tokens[T_max]`, RNG
counter, speculative bookkeeping (`draft_tokens`, `accepted`, GDN checkpoint index), `done`, `error`, token-ring head.

* The last dispatch of a step is `SERIAL`: finalize sampling, run accept/reject, choose the GDN checkpoint to keep,
  append to the **token ring** (shared memory — the CPU reads it without a copy), check stop conditions (EOS set,
  max length, stop-token table), advance positions and `step`.
* **Host pump.** The host keeps a few command buffers in flight (≈ 50–100 ms of queued work), each replaying one
  bounded range of the step ICB (§5.1). A completion handler drains the token ring and enqueues more. When `done` is set, steps already queued return at their first
  instruction (~2 µs per dispatch). The host never waits on the GPU to decide what runs next, so host latency is off
  the critical path.
* **Prompt processing** in v1 reuses the decode program with T = T_max per step (decode-shaped kernels, as MPK's dense
  lane and the Hopper port do). A dedicated prefill path (tiled GEMM / MPP TensorOps, FlashAttention-style SDPA,
  chunked GDN scan) is post-v1 — prefill is explicitly not a v1 gate.

### 5.5 Memory and weight layout

* **Weights** are converted once into `weights.pack`, page-aligned and mmap'ed straight into a few large `MTLBuffer`s
  (`newBufferWithBytesNoCopy`; each below `maxBufferLength`, 21 GiB on the M3 Pro), one residency set.
* **Block-lane-major (BLM) pack.** For a matrix `[N, K]` with R-row blocks: block `b` holds rows `[bR, bR+R)`; inside a
  block, data is ordered *by lane, then row*: lane ℓ's column stripe `[ℓK/32, (ℓ+1)K/32)` of all R rows, then that
  stripe's scales. A lane reads one contiguous ~1–2 KB range per block and the SIMD-group sweeps one contiguous
  ~32–64 KB block — the access pattern that streamed at 124–134 GB/s **[M]**. Fusions are layout decisions too: gate and up
  rows are interleaved so one pass yields `silu(g)·u`; `q|k|v` and `in_proj_qkv|a|b` are row-stacked into single ops.
  The mixer's gate projection (`in_proj_z`; the gate half of `q_proj`) is stacked with them or packed as its own op,
  depending on whether §5.12's sibling overlap is enabled for the chip. R, stripe order and scale placement are
  autotuned per chip.
* **Formats** are plugins: `unpack(checkpoint tensors) → pack` plus an MSL `decode` snippet used by the GEMV
  template. v1: NVFP4 (E2M1 LUT × E4M3 block scale × FP32 tensor scale), FP8-E4M3 per-tensor (256-entry LUT), BF16.
  Next: MXFP4, affine INT4/INT8 groups (MLX/AWQ/GPTQ), GGUF K-quants.
* **State.** KV cache per attention layer (BF16 in v1; FP8/INT8 later — at long context KV traffic overtakes the
  weights); GDN recurrent state FP32 `[48,128,128]` + conv state, each with `k+1` checkpoint slots for speculative
  rollback; activation arena planned by liveness (a few MB); `StepState`; optional trace buffer.

### 5.6 Decode kernel library (v1)

| Op | Block | Notes |
|---|---|---|

| `gqa_decode` | (q-head, KV-chunk) | online-softmax `(m, d, o)` state merge (FlashInfer / MPK `gqa_decode_sm100_v2`), per-head q/k norm, partial RoPE via the load-time head-dim permutation, KV append, sigmoid output gate |

M5 path **[H]**: for T > 1 (verify, prompt chunks) the GEMM block can dequantize into a cooperative tensor and call
`matmul2d<desc, execution_simdgroups<N>>` so the per-core neural accelerator is used; the autotuner selects it when
it wins. Apple's native quantized tensor types (macOS 27: FP4/FP8 with E8M0 block-32 scales) do not match NVFP4's
E4M3 block-16 + tensor scale, so NVFP4 stays on our decode path.

### 5.7 Compiler

* **IR.** Typed tensor graph; shapes symbolic in `T` and context length; ops carry reads/writes, block domain, class
  and a cost model. Layers of the same type share one op template plus a per-layer weight-slab table (PR #278's
  layer-type templating), so the kernel set is independent of depth: ~12 pipelines serve all 64 layers.
* **Passes.** canonicalize → fuse (vertical chains, norm folding, epilogues, row-stacking) → select weight packs →
  partition into block domains → place barriers (only on real dependencies; independent ops may run concurrently
  inside the ICB) → plan memory → emit.
* **Emit.** Hand-written, tested *block bodies* + generated kernel wrappers specialized by function constants;
  `program.json`; pack manifest. Pipelines are compiled at install/first run and cached in an `MTLBinaryArchive`.
  Math mode is `safe` for softmax/norm/sampling bodies (MSL fast-math is on by default **[S]**) and may be relaxed in
  GEMV inner loops if the layer gates hold.
* **Chip profiles.** `{cores, full-speed SIMD-groups per core, GB/s, block sizes, R, T_max, k}` — produced by the
  probe suite and an autotuner at install time, never hard-coded.

### 5.8 Speculative decoding with the MTP head

Round = draft k tokens with the MTP layer (0.85 GB BF16 + the shared `lm_head` per draft token, ~9 % of a main pass;
optionally re-quantized to FP8 at load) → one main pass at T = k+1 → on-GPU strict verify (greedy) or rejection
sampling → keep GDN checkpoint `accepted`, advance KV by `accepted + 1`. Every piece is a step-program op, so a round
is replayed like any other step; acceptance changes only `StepState`. T = 2–4 roughly triples ALU work per weight byte
while traffic is unchanged — affordable on bandwidth-bound Pro/Max parts and exactly the regime M5's accelerators
target **[H]**. This is not guaranteed to pay: llama.cpp's MTP speculation is reported as a net loss on an M1 Max
**[R]**, so k is chosen per chip by measurement and the gate is tokens/s, not acceptance rate. Correctness gate:
token-identical to non-speculative greedy decode.

### 5.9 Numerics, correctness, determinism

* Reference = HF `Qwen3_5ForConditionalGeneration` on weights dequantized exactly as the pack decoder does
  (NVFP4: `LUT[q] · scale_e4m3 · scale_2`; FP8: `LUT[w] · scale`). Small same-architecture models serve end-to-end CI;
  the 27B is checked layer by layer (`--num-layers-override`) and by greedy-token match.
* Gates inherited from MPK: leaf ops vs a torch oracle (≤ 2 ULP BF16 outputs, ≤ 8 ULP FP32 state); composite layers
  cos > 0.999 with bounded max-abs; full-model greedy tokens equal to the golden except at exact logit ties; repeated
  runs bit-identical.
* Static slices (and stealing, where used) change only *who* computes a block, never the arithmetic inside it;
  reductions combine per-block partials in block order. Results are bit-deterministic.

### 5.10 Profiling and debugging

* Every op is its own dispatch, so per-op GPU timestamps come straight from counter sample buffers (one encoder per
  op in profiling builds), and Xcode GPU capture and shader validation work normally.
* For intra-op detail a **clock SIMD-group** free-runs an atomic tick counter; workers stamp block begin/end. Ticks
  are calibrated against the command buffer's `GPUStartTime/GPUEndTime`. Compile-time switch only (PR #278: a runtime
  profiling flag cost 0.4–0.5 ms/step).
* Output is `.mpktrace`; MPK's decoder and Canvas viewer are reused with tracks = (core, SIMD-group).
* Perf methodology from MPK: paired alternating A/B runs, min-of-N, never a single sample; report GB/s streamed and
  % of the chip's bound next to tok/s.

### 5.11 Extending the engine

| To add | You write | You do not touch |
|---|---|---|
| a model built from existing ops | a Python `Module` tree (`forward`, `lower`, weight-name map + transforms), a config dataclass, a registry entry, an HF golden script | kernels, runtime, compiler |
| a quantization format | a format plugin (unpack → BLM pack; MSL `decode` snippet) + oracle test | GEMV template, models |
| a new op (MoE router/experts, MLA, sliding-window attention…) | a block body in MSL + IR op (domain, class, cost) + `forward` oracle + leaf test | runtime, other ops |
| a new chip | run the probe suite + autotuner → profile | everything else |

MoE fits the static program: routing is a `REDUCE`+`SERIAL` pair writing expert ids to a buffer; expert GEMVs are `MAP`
ops whose blocks index the expert slab through those ids (PR #278's `dyn` ops) — no re-encode, no CPU. Their uneven
blocks are the natural first customer for intra-op stealing.

### 5.12 Inter-op overlap: what MPK V2's software pipelining becomes here

MPK V2 pipelines *across dependencies*: while op k computes or waits on its activations, loader warps stage op k+1's
weights into SMEM, so weights are never what a task waits for. Three measurements (`probes/p11_interop_overlap`, M3
Pro) say which part of that idea survives on Apple silicon:

| Measurement | Result | Meaning |
|---|---|---|
| Streaming rate vs cores used | 1 core 18.0–18.7 GB/s; 9 of 18 cores 114–126 GB/s; 12–18 cores 123–133 GB/s (up to 87 % of nominal) | the bus saturates with half to two-thirds of the cores — the rest of the ALUs idle during every bus-bound op |
| Bus-bound op ∥ bus-bound op, no barrier | 118–131 GB/s serial vs 126–131 (split cores) / 127–130 (oversubscribed): no consistent gain | **overlap cannot create bandwidth**: pre-staging op k+1's weights would only take bus time from op k — and there is no faster memory to stage them into (P8) |
| Bus-bound op ∥ ALU-bound op, no barrier, both at full crew geometry | serial 27.3 ms → overlapped 24.7 ms = the bus-bound op alone; **the ALU op fully hidden (86–114 % across runs, i.e. within noise)**, even when it is 87 % as long as its partner, in either encode order | the hardware interleaves SIMD-groups of the two dispatches on each core and fills memory-latency gaps with ALU work |
| Same pair with cores split by hand (15 ∥ 3, or 12 ∥ 6 encoded ALU-first) | 31.2 ms and 29.0 ms — *slower* than serial | placement belongs to the firmware; do not partition cores |

So V2's pipelining across dependencies does not transfer (D14), but one overlap does, and the model's dataflow offers
exactly one instance per layer: the token mixer's core is ALU/latency-bound at short context and its *gate* projection
is a bus-bound GEMV that the core does not depend on —

* GDN layer: conv → L2-norm → delta-rule recurrence needs `q, k, v, a, b`; `in_proj_z` (31 MB FP8) is consumed only by the
  final gated norm. Emit `in_proj_z` as an un-barriered sibling of the recurrence instead of row-stacking it with `qkv`.
* Attention layer: the attention core needs `q, k, v`; the output-gate half of `q_proj` (31 MB FP8) is consumed only by
  the final sigmoid gating. Same treatment. (At long context attention itself becomes bus-bound and the pair stops
  overlapping usefully.)

Expected value **[H]**: the mixer core is a few percent of a layer, so ~2–4 % of a step on the M3 Pro. It is a compiler
rule (do not stack a projection whose only consumer sits behind an ALU-bound op), costs +64 un-barriered dispatches, and
is enabled per chip by measurement.

**M4 and M5 — projected, not measured.** What matters is how over-provisioned the cores are relative to the bus, i.e.
nominal GB/s per GPU core; a core's uncontended streaming rate was ~18 GB/s here:

| Chip | GB/s per GPU core | Expected spare ALU during a bus-bound op |
|---|---|---|
| M3 Pro 18c (measured) | 8.5 | 33–50 % |
| M3 Max 40c / M3 Ultra 80c | 10.2 | large |
| M4 10c | 12.0 | small |
| M4 Pro 20c / M4 Max 40c | 13.7 | small |
| M5 10c / M5 Pro 20c / M5 Max 40c / M5 Ultra 80c | 15.4 | little or none, unless Apple10 cores stream faster than Apple9 |

Apple has raised bandwidth faster than GPU core count, so M4/M5 GPUs are *less* bus-starved per core than the M3 Pro:
there is less idle ALU to harvest, a quantized GEMV is closer to needing every core, and an overlapped ALU-bound op is
more likely to slow its partner than to hide in it. The same fact predicts that speculative verification turns
ALU-bound at a smaller T on M4 — and explains why M5's per-core neural accelerators matter for T > 1. M5 adds one
opportunity with no M3/M4 counterpart **[H]**: inside a T > 1 GEMM, dequantizing the next tile on the shader ALUs while
the accelerator multiplies the current one (MLX's `quantized_nax` does these sequentially) — the closest Apple analogue
of Blackwell's loader/mma split, relevant to verification and prefill, not to T = 1 decode. Both projections are
settled by running `p11` (sections 1 and 3b) on the hardware.

## 7. The two questions

### 7.1 Should we use warp specialization on Apple silicon? — No.

Specialization in MPK is not an end in itself; it is how software drives *heterogeneous, asynchronous* hardware from
inside a kernel: the loader warp feeds the copy engine, the mma warp feeds tensor cores, the storer drains results
while the compute warps work, and SMEM is the software-managed buffer between them. We looked for each of those on
Apple silicon:

* **A fast scratchpad to stage into?** No — threadgroup memory costs the same as device memory **[M]**; Apple9+
  serves registers, threadgroup memory, stack and buffers from shared hardware-managed caches **[S]**.
* **An asynchronous copy or matrix engine?** No — MSL has no copy instruction; on M3/M4 `matmul2d` runs on the ordinary
  ALUs (1.05–1.21× over `simdgroup_matrix`) **[R]**; on M5 the accelerator sits inside each shader core and is invoked
  as a *collective of the calling SIMD-groups* **[S]**. This is the Hopper situation (`wgmma` is
  warpgroup-collective, so the compute warps issue it and the mma warp idles) taken to its conclusion.
* **Work to overlap?** Decode is a chain of ops that each saturate the one shared resource, the memory bus. A
  SIMD-group diverted to a side role is 1/216 of the streaming capacity lost, and a *spinning* one burns power with no
  `__nanosleep` to soften it.
* **Something to coordinate?** With one dispatch per op there is no in-kernel coordination left for a dispatcher or
  storer role to perform.

So the crew is homogeneous. What does carry over from warps is the discipline: the SIMD-group is the unit of control
flow and of cooperative kernels (32 lanes = 32 column stripes of a block), and kernels are written to its lockstep
rule. The single exception is diagnostic: the **clock SIMD-group** in profiling builds.

*What would change this:* a GPU generation exposing an asynchronously driven engine or a software-managed memory
level, or a CPU/ANE co-execution scheme that needs a GPU-side feeder. Neither exists today.

### 7.2 Should we use the static megakernel approach (PR #278)? — Static: yes. One kernel: no.

* **Static — yes.** The schedule is fixed at compile time and replayed; there is no dispatcher, instruction ring or
  task descriptor. On a single symmetric GPU running a dependency chain, a dynamic scheduler has nothing to schedule
  around: PR #278's own ledger shows V2's remaining edge was *concurrency* ("hiding producer readiness by running
  other ready tasks on stalled workers" across 148 SMs × 8 ranks with all-reduce skew) — a regime that does not exist
  here. We add what PR #278 lacked: the schedule is **compiler-generated**, which is both the generality requirement
  and the cure for its hand-maintained-invariant bugs (event-id collisions, aliased enums, out-of-range SM placements).
* **One kernel — no, for three independent measured reasons.** (1) A dispatch boundary (1.6–2.7 µs) is never
  meaningfully dearer than an in-kernel barrier (2.1–2.6 µs unfenced, 3.1–3.9 µs in the form the spec requires,
  4.7–6.1 µs with stealing), and with real work per block the difference vanishes — merging ops cannot win. (2) The
  GPU is never shared within a dispatch, so a long kernel freezes every other client and invites the watchdogs. (3) Nothing is lost
  by returning: there is no fast-memory state to keep warm between ops, unlike SMEM rings and TMEM accumulators.
  PR #278 paid for its single launch with launch-lifetime rings and event math; here the firmware provides sequencing
  for free.
* **What "megakernel" means on Apple.** The unit that is compiled, fixed and GPU-resident is the *step program*, not
  a kernel: encoded once, replayed without CPU work, self-advancing, with sampling and speculative control on the GPU.
  That delivers the properties PR #278 was after — zero dispatch overhead on the host, no per-task synchronization
  lifecycle, a static whole-model schedule — through the mechanism this hardware makes cheapest.

*What would change this:* a chip/OS where dispatch boundaries are much more expensive than in-kernel barriers
(re-measured per chip by `p10`), multi-request serving with divergent per-request control flow, or multi-device
tensor parallelism over a fabric with skew — the regime where V2's dynamic scheduler earned its keep.

## 8. Risks and open questions

1. **The bandwidth result is a microbenchmark.** BLM + crew geometry = +5 % to +17 % on raw reads; real NVFP4/FP8 GEMV must
   reproduce it against MLX `qmv` (plan M1, go/no-go). If it does not, the decode win reduces to fusion + speculation.
2. **Per-load latency.** ~40–60 ns per memory load per lane **[M]** makes low-bit GEMV ALU/load-bound on Pro-class
   parts unless loads are wide and activations are reused across R rows × T tokens.
3. **Undocumented firmware behaviour.** One threadgroup per core, 12 full-speed SIMD-groups, dispatch-granularity
   sharing: observed on one chip. Design rule: *correctness depends only on documented Metal semantics* (dispatch
   ordering and ICB barriers); everything else is a per-chip profile.
4. **ICB maturity.** Compute ICBs are lightly used in production: tinygrad is the only surveyed engine that ships one,
   it needs a zero-size-dispatch workaround on M1/M2 (not on Apple9+), bind offsets are 32-bit, and two Apple-forum bug
   reports are unanswered **[R]**. Fallback: re-encode the same program each step (0.16 ms/token **[M]**, still no
   synchronization).
5. **Sharing is best-effort.** Other clients usually run between our dispatches, but one trial in six waited for a
   whole command buffer; the compositor's own behaviour was not measured. Command-buffer length is the control, and an
   on-screen frame-pacing check (plan M0) sets its default.
6. **Speculation on compute-poor chips.** T = 2–4 verification may turn base/Pro parts compute-bound; MTP acceptance for
   this checkpoint is unmeasured. Gate on tokens/s, not acceptance rate.
7. **Long context.** KV traffic is 64 KB × context per step; beyond ~64 K it rivals the weights. KV quantization and a
   better long-context attention block are post-v1.
8. **Memory headroom.** 21 GB of weights + state on a 36 GB machine (28–30 GB working set) is fine; 32 GB base chips are
   tight; 24 GB does not fit.
9. **Reference semantics.** NVIDIA's runtime quantizes activations (W4A4/W8A8); ours does not. Token-level agreement
   with Blackwell outputs is not a goal; accuracy parity on a small eval set is.
10. **Baselines move.** MLX already has NVFP4 kernels and M5 TensorOps paths; llama.cpp follows. Baselines are
   re-measured at every milestone; every claim is relative, same machine, same day.
